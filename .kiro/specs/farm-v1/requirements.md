## 1. 产品范围

Farm v1 面向单个局域网打印农场，提供本地账号、打印机管理、打印文件库、打印任务、设备控制和实时状态看板。

角色只有：

- `ADMIN`：管理本地账号、打印机配置、文件、任务和设备。
- `OPERATOR`：查看设备，操作本人资源，并执行允许的现场打印控制。

不包含公开注册、手机号/邮箱验证、多租户、互联网账号中心和复杂 RBAC。

## 2. 现状与完成标记

- 前端工程内的基础接入、页面联调、WebSocket 自动重连和告警展示；当前仓库不包含前端工程。

## 3. 需求列表

### REQ-01：统一公共接口契约

系统必须维持 `/api/v1` 公共前缀、Bearer JWT 认证、统一响应结构、统一分页格式、冻结后的打印机/任务状态枚举和 API_HANDOFF 中登记的角色权限。

验收条件：

1. 新增接口不使用未登记的响应包装或字段命名。
2. 成功无业务数据时 `data=null`，不返回随机成功字符串。
3. 400、401、403、404、409、422、503 等错误同时具备正确 HTTP 状态和业务码。
4. API_HANDOFF 与 OpenAPI/Controller 实际行为一致。

### REQ-02：协议适配与设备能力

系统必须通过统一内部适配器支持 `KLIPPER` 和 `RRF`，并覆盖状态查询、暂停、恢复、取消、急停、上传和启动能力。

验收条件：

1. Controller、任务 Service、监控任务不直接依赖具体协议客户端。
2. 历史 `Klipper` 值可以规范化为 `KLIPPER`。
3. 未知协议不会回退到 Klipper。
4. Klipper 现有能力经过改造后行为不回退。
5. RRF 真实 API 路径、认证和字段只有在官方资料或真实设备证据确认后才能标记为完成。

### REQ-03：设备状态和错误一致性

系统必须把不同协议状态映射为 `OFFLINE`、`IDLE`、`PREPARING`、`PRINTING`、`PAUSED`、`ERROR`、`UNKNOWN`，并统一表达离线、超时、忙碌、协议不支持和非法业务状态。

验收条件：

1. 任务只有在设备操作成功后才进入 `PRINTING`。
2. 一台设备离线不会阻塞或污染其他设备监控。
3. 设备错误不会被静默吞掉为成功。
4. 日志不输出凭据、JWT、密码或对象存储内部 key。

### REQ-04：WebSocket 实时状态

系统必须在 `/ws/farm-status` 提供经过 JWT 鉴权的农场级实时状态推送，消息类型固定为 `SNAPSHOT`、`PRINTER_STATUS`、`PRINTER_OFFLINE`、`JOB_STATUS`。

验收条件：

1. 有效连接成功后收到一次包含全部设备的 `SNAPSHOT`。
2. 状态变化、离线和任务状态变化使用统一顶层结构。
3. `timestamp` 使用 Unix epoch 毫秒，状态枚举与 REST 一致。
4. 断线、发送失败和超过连接上限的会话被清理或拒绝。
5. 推送失败不影响数据库事务，前端可以通过 REST 重新同步。

### REQ-05：打印机管理增强

系统必须支持已登记打印机的详情、状态历史、统计、暂停、恢复、取消和急停，并继续执行角色、设备状态和协议能力校验。

验收条件：

1. 新接口地址、参数和返回结构冻结在 API_HANDOFF。
2. 控制操作都经过 Service 和 Adapter。
3. ADMIN/OPERATOR 权限与现有策略一致。
4. 设备离线、忙碌、错误时返回明确错误码。

### REQ-06：文件库增强

系统必须支持文件筛选、目录树、文件关联任务、安全预览和下载，并保持文件归属隔离、上传限制和敏感字段保护。

验收条件：

1. 名称和材质筛选真实生效。
2. `folder` 字段命名统一，内部 RustFS key 不出现在响应。
3. 删除已关联任务的策略明确且有测试。
4. 下载 URL 有权限校验和有效期上限。

### REQ-07：任务队列和安全打印流程

系统必须支持标准创建、队列查询、派发、安全确认、启动、取消、重试、重新排队和优先级调整。

验收条件：

1. 任务只使用冻结的 8 个状态。
2. 标准地址为 `POST /api/v1/print-jobs`，旧 `/create` 兼容保留并标记 deprecated。
3. `operatorId` 由当前 JWT 用户决定。
4. 任务归属、文件归属、打印机忙闲和状态转换均由后端校验。
5. 状态变化在持久化成功后发送 `JOB_STATUS`。

### REQ-08：认证与用户管理

系统必须支持本地登录、管理员创建操作员、启用/禁用、角色管理、个人资料和修改密码。

验收条件：

1. 用户响应不包含密码哈希。
2. 密码规则由后端强制执行。
3. ADMIN-only 接口对 OPERATOR 返回 403。
4. 禁用用户、登录失败保护和 Token 错误返回统一响应。

### REQ-09：前后端联调

前端必须能够依据 API_HANDOFF 完成登录、设备看板、文件库、任务队列和权限菜单接入。当前后端仓库不假设前端代码路径，前端任务必须在真实前端仓库中记录文件位置。

验收条件：

1. HTTP 客户端统一发送 Bearer Token 并解析统一响应。
2. 401/403/404/409/422/设备错误有统一提示。
3. WebSocket 先 REST 初始化，再按消息类型增量更新。
4. 前端不读取 `apiKey`、`rustfsKey`、密码等内部字段。

### REQ-10：测试、迁移和运维

系统必须具备与风险相称的自动化测试、可复现启动方式、数据库升级说明、健康检查和安全生产配置。

验收条件：

1. 核心 Controller、权限、Service、状态机、Adapter、WebSocket 和端到端链路有测试。
2. 没有真实设备时使用 Mock/Stub，不把 Mock 结果当真实设备支持。
3. Docker 数据卷不被无授权删除，迁移有备份和回滚说明。
4. 生产密钥、CORS、Swagger、日志和文件存储配置有明确说明。

## 5. 产品裁剪规则

第一版允许保留以下边界：

- WebSocket 只做农场级广播，不做按打印机订阅。
- 登出可以先由前端删除 Token，不实现 Token 黑名单。
- RRF 真实控制能力按实际 API 逐项完成，不强行一次覆盖全部能力。
- 状态历史和统计可以在协议适配完成后作为独立 P1 Task 实现。

任何其他未完成项若要裁剪，必须在 `TODO.md`、`tasks.md` 和 API_HANDOFF 中记录原因与替代方案。
