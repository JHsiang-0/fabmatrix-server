# Farm v2 需求规格：手动优先的打印农场

## 1. 背景与范围

Farm 是部署在局域网的本地服务端，多个客户端共享打印机、文件库、打印任务和实时状态。v2 不改变本地部署定位，也不引入手机号注册、公开注册、多租户或云端账号体系。

v2 的核心调整是把业务收口为两条用户主动操作路径：单任务手动上传和手动选择打印机是默认路径；批量匹配是用户发起、预览和确认的操作。后台自动派单不属于 v2，延后到 v3 重新设计。

## 2. 角色

- `ADMIN`：管理本地账号、设备配置和全部业务数据；后台自动派单属于 v3，不在 v2 提供管理入口。
- `OPERATOR`：查看设备和文件，上传文件，手动创建/分配/控制自己有权限操作的任务。

后端权限仍以 JWT 和服务层校验为准，前端隐藏按钮不能代替鉴权。

## 3. 需求

### REQ-01 手动优先的派单模式

系统必须提供明确的 v2 派单模式：`MANUAL`、`USER_BATCH`。用户主动触发的 `AUTO_MATCH` 是 `USER_BATCH` 下的一种匹配策略，不是后台调度。

验收标准：

- 新安装或配置缺省时，默认是 `MANUAL`，后台不自动分配任务。
- `USER_BATCH` 只能由用户主动点击触发，并且必须经过预览和确认。
- v2 不提供后台自动派单入口和执行接口；现有调度代码必须默认关闭且不能因配置缺省值误启动。
- 后台自动派单及其授权、审计和执行规则列入 v3，不作为 v2 验收项。

### REQ-02 单任务手动流程

用户必须能选择一个已上传文件和一台打印机，创建任务并按“派发 → 安全确认 → 上传/启动”的顺序操作。

验收标准：

- 打印机不存在、离线、被占用或协议不匹配时，操作失败且返回可识别的业务错误。
- `UPLOAD_ONLY` 只上传到设备，不启动打印；启动必须由用户显式调用。
- `START_PRINT` 必须检查任务状态、打印机状态、操作者权限和安全确认。
- 暂停、恢复、取消和急停都必须同时记录设备调用结果和 Farm 可观察状态。

### REQ-03 批量文件上传

系统必须支持用户一次上传多个文件，并为每个文件返回独立结果。

验收标准：

- 单文件扩展名、大小、空文件和内容解析校验失败时，不影响其他文件结果。
- 响应包含成功文件 ID、失败原因、重复文件提示和是否可以重试。
- 上传接口必须使用统一文件存储抽象和文件归属规则；Server Edition 使用 RustFS，Local Edition 使用受控的 Windows 本地目录，不将本地临时路径暴露给前端。
- 批量大小和文件数量有明确上限，超过上限返回参数错误。

### REQ-04 用户发起的批量分配预览

用户必须能选择多个文件、多个打印机和匹配策略，先获取不产生副作用的分配预览。

验收标准：

- 至少支持 `ONE_TO_ONE`、`ROUND_ROBIN`、`AUTO_MATCH` 三种策略。
- 预览返回每个文件与打印机的候选关系、冲突、不可用原因和计划过期时间。
- 预览阶段不创建打印任务，不锁定打印机，不上传设备，不启动打印。
- 预览必须重新读取设备/任务占用的可信数据，不能只依赖可能过期的 Redis 全量列表缓存。

### REQ-05 批量分配确认与逐项结果

用户确认预览计划后，系统才可以创建任务、绑定打印机并执行选择的上传动作。

验收标准：

- 确认请求必须带计划 ID、版本/确认令牌和要执行的项，过期或内容变化时拒绝执行并要求重新预览。
- 确认过程具备幂等性，重复提交不会重复创建任务或重复占用打印机。
- 返回每项的任务 ID、设备 ID、动作、状态、错误信息和重试建议。
- 某一项失败不能吞掉其他项结果；系统必须保留已成功项。
- 默认动作不直接启动打印；需要启动的项必须进入安全确认流程。

### REQ-06 后台自动派单的 v2 安全边界

v2 不实现后台自动派单，但必须防止现有调度代码在 v2 运行时误改变任务或打印机绑定。

验收标准：

- `farm.scheduler.enabled` 固定缺省为 `false`，且不会因旧的 `matchIfMissing=true` 误启动。
- 设备监控开关与调度器开关必须独立，监控开启不能带起调度器。
- v2 前端不展示后台派单设置，v2 API 不提供后台派单执行入口。
- v3 重新设计后，才决定是否提供管理员授权、计划确认和审计规则。

### REQ-07 监控与设备白名单

设备监控必须支持只监控指定设备，并能在没有真实设备时安全关闭。

验收标准：

- 监控任务只轮询允许列表中的打印机，不扫描数据库中所有历史设备。
- 设备不可达会更新设备健康/最后在线信息，但不会让监控线程退出或阻塞其他设备。
- 监控读取任务绑定时以数据库最新值为主，缓存更新必须有明确失效策略。
- 监控与调度器分别拥有开关、日志和测试入口。

### REQ-08 协议适配与任务生命周期

Klipper/Moonraker 和 RRF 必须通过统一设备能力接口接入，协议差异不能泄漏到 Controller。

验收标准：

- 适配器提供状态快照、上传、启动、暂停、恢复、取消、急停和连接检查能力。
- RRF `idle` 不能单独被认定为打印完成；完成必须有文件完成、进度或设备历史等证据。
- 取消/急停需要区分“请求已发送”和“设备已确认”，连接中断时任务进入可恢复的中间状态。
- 设备原始状态、统一状态、任务最终状态和状态来源可追踪。

### REQ-09 并发、幂等和恢复

多个客户端、监控线程和可选调度器同时操作时，系统必须保持资源一致性。

验收标准：

- 同一打印机不能被两个任务成功绑定。
- 确认、启动、取消等重复请求具有幂等结果。
- 进程重启后，中间状态可通过设备查询和人工重试恢复，不产生幽灵占用。
- 分配失败、设备离线和上传失败都有明确的回滚或待处理状态。

### REQ-10 REST 与 WebSocket 状态契约

前端必须能用 REST 获取权威快照，用 WebSocket 获取增量状态。

验收标准：

- REST 和 WebSocket 使用同一套统一状态枚举和字段命名。
- WebSocket 消息包含版本、事件类型、设备/任务 ID、发生时间和数据快照或变更字段。
- 前端断线重连后可以通过 REST 快照纠正丢失的事件。
- WebSocket 失败不影响手动上传、分配和控制接口。

### REQ-11 认证、权限和数据归属

所有业务写操作必须经过认证、角色校验、参数校验和服务层资源校验。

验收标准：

- 未登录返回 401，角色不足返回 403，业务状态冲突返回稳定业务错误码。
- 批量接口逐项检查文件归属、打印机权限和任务权限。
- 操作员不能通过请求体伪造 `operatorId` 或访问无权限资源。
- 日志不记录密码、JWT、API Key 或对象存储密钥。

### REQ-12 测试、文档和运维

每个新 Task 必须有针对性测试、文档状态和可复现的验收条件。

验收标准：

- Controller 权限/参数测试、Service 并发/幂等测试、协议适配器测试覆盖核心分支。
- 真实设备控制、上传、启动、暂停、急停只在用户指定的真实 RRF 设备上验证；模拟板不作为打印机验收依据。
- Swagger、`API_HANDOFF.md`、`TODO.md` 和 `tasks.md` 的已实现状态一致。
- 开发环境默认不会因为没有真实设备而自动产生轮询和调度错误。

### REQ-13 双部署形态

系统必须同时规划 v1 Server Edition 和 v2 Local Edition，二者共用业务 API、权限模型和打印机协议适配层。

验收标准：

- v1 Server Edition 可以使用正式 Docker Compose 启动 Farm 后端、MySQL、Redis 和 RustFS；敏感配置通过环境变量注入，数据通过命名卷持久化。
- Server Edition 的 MySQL、Redis、RustFS 默认不直接暴露到宿主机，只由 Farm 后端访问；需要对外访问时必须有明确配置和安全说明。
- v2 Local Edition 使用 SQLite 保存业务数据，使用 Windows 本地目录保存 G-code 和缩略图，不要求安装 Docker、MySQL、Redis 或 RustFS。
- Local Edition 在单个 Farm 后端进程、多个局域网客户端的范围内支持事务、文件归属、批量操作和备份恢复。
- 两种部署形态对前端保持相同的 REST/WebSocket 契约；部署模式不能改变任务状态和权限语义。
- SQLite/MySQL、本地文件/RustFS 的切换通过服务接口和配置完成，不能在 Controller 中写死具体存储实现。

## 4. 非目标

- 手机号、邮箱、公开注册、找回密码服务。
- 云端 SaaS、多租户、注册中心和跨农场联网。
- 未经用户确认的后台自动启动打印。
- 后台自动扫描队列、自动匹配和自动派单；这些能力延后到 v3。
- 用一个协议客户端通过修改 URL 的方式假装支持所有固件。
