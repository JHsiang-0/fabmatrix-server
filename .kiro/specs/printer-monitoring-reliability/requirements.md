# 打印机监控可靠性需求规格

状态：已实现，待真实设备联调

## 1. 背景与范围

当前 `PrinterMonitorTask` 通过 `farm.monitor.printer-ids` 配置白名单决定轮询范围。白名单为空时不监控任何设备，前端不能动态管理监控目标。打印机通信状态、设备业务状态和任务最终状态也没有完全分离，断网、设备重启、RRF `idle` 和 Klipper/Moonraker 状态恢复时存在误判风险。

本规格是 `farm-v2` 监控实现的后续改造，不改变局域网本地部署定位、ADMIN/OPERATOR 角色、手动优先的任务流程，也不实现后台自动派单。

## 2. 需求

### REQ-01 前端可管理监控目标

系统必须支持通过受保护的 REST 接口启用或停用单台、批量打印机监控。

验收标准：

- ADMIN 可以查询和修改打印机监控开关；OPERATOR 只能查看。
- 单次批量修改最多 100 台设备。
- 批量 ID 不得为空或包含 null；重复 ID 去重，返回实际涉及的唯一设备数。未知 ID 或任一写入失败时整体回滚，不返回部分成功。
- 修改监控开关只更新开关和修改时间，不能覆盖任务绑定、安全确认、设备状态或通信健康；缓存只在事务成功提交后刷新。
- 监控目标从数据库读取，配置文件只保留总开关、轮询参数和并发参数。
- 已废弃或没有有效 IP 的打印机不能被轮询。
- 无 IP、空字符串或纯空白地址的设备仍可保存监控开关，但不会进入轮询目标；修改开关不执行设备探测或控制。
- 新增打印机可以默认进入可监控状态；历史数据不得因为迁移自动对所有记录发起请求。

### REQ-02 通信状态与业务状态分离

系统必须分别表达“能否与设备通信”和“设备正在做什么”。

验收标准：

- 通信失败只更新连接健康字段，不把设备当前业务状态直接改成新的业务结论。
- 设备断网时保留最后已知业务状态、当前任务绑定和最后成功通信时间。
- REST 和 WebSocket 同时返回 `connectionStatus`、`status`、`lastKnownStatus` 和必要的健康信息。
- `OFFLINE` 不能被后台调度当作 `IDLE` 使用。

### REQ-03 通信失败与恢复

系统必须隔离短暂网络抖动，并支持设备恢复后的状态收敛。

验收标准：

- 单次超时不能立即产生永久离线结论。
- 连续失败次数、最近错误和最后成功时间可查询。
- 连续成功达到恢复阈值后恢复 ONLINE。
- 单台设备超时不能阻塞或取消同一轮其他设备巡检。
- 监控程序重启后，状态可以从数据库和设备重新收敛。

### REQ-04 任务恢复与人工核对

当 Farm 有活动任务绑定但设备返回空闲、重启或无法提供足够证据时，系统必须保留绑定并进入可人工处理的 `RECONCILING`。

验收标准：

- API 完全不可达时，任务不自动变为 FAILED、COMPLETED 或 CANCELLED。
- 设备恢复后返回明确完成证据时才自动完成任务。
- 设备文件名与 Farm 任务不一致时不得更新任务进度。
- 设备重启后只有 `idle/standby/ready` 而没有完成证据时进入 `RECONCILING`。
- 人工核对支持 COMPLETED、FAILED、CANCELLED 和重新 QUEUED，并安全处理打印机绑定。

### REQ-05 Klipper/Moonraker 兼容

监控必须支持 Klipper + Moonraker 的系统状态和打印状态。

验收标准：

- 读取 `webhooks`、`print_stats`、`display_status` 和可用的温度对象。
- `webhooks.state` 非 `ready` 时表达系统启动、故障或不可用，不覆盖为正常打印状态。
- `print_stats.state=complete` 可以完成匹配的 Farm 任务。
- 缺少必要对象时返回可定位的协议配置错误，不静默伪装成空闲。
- 状态查询失败、Moonraker 重启和 Klipper 重启均有测试覆盖。

### REQ-06 RRF 兼容

监控必须正确处理 RRF 的状态、文件进度和不确定的 `idle`。

验收标准：

- 正确解析 `job.filePosition`、`job.file.size`、`job.timesLeft.file`。
- 支持读取 `job.lastFileName`、`job.lastDuration`、取消/中止标记和设备运行时间（设备支持时）。
- RRF `idle` 不能单独作为完成凭证。
- 正常完成、取消、急停、断网和重启场景均保留可解释的状态来源。
- Standalone 模式缺少 DSF/DWC 字段时仍然安全降级到人工核对。

### REQ-07 轮询性能与多实例安全

系统必须避免历史无效设备和多实例重复轮询造成资源浪费。

验收标准：

- 轮询只选择已启用、协议支持且有有效地址的设备。
- 打印中、空闲、离线设备支持不同的轮询频率或退避策略。
- 多实例不能无锁地重复轮询同一设备。
- 连续离线日志和 WebSocket 事件具有限频和去重机制。
- 监控结果包含耗时、在线数、离线数、失败数和跳过数。

### REQ-08 权限、迁移和兼容性

改造必须符合本地农场权限和数据库升级约束。

验收标准：

- 监控管理接口由 `SecurityConfig` 和 Service 双重保护。
- 不信任请求体中的用户身份或操作员 ID。
- 数据库变更使用显式增量 SQL，不依赖 Flyway 自动执行。
- 不删除现有打印机、任务和状态历史数据。
- 旧 `farm.monitor.printer-ids` 配置不会导致未知设备被意外轮询。

### REQ-09 测试与契约

系统必须补充针对性的单元、Controller、协议和集成测试，并更新 API 交接文档。

验收标准：

- `mvnw.cmd test` 通过。
- 覆盖权限、输入校验、状态恢复、协议字段和并发边界。
- Swagger/OpenAPI、`API_HANDOFF.md` 和实际 Controller 保持一致。
- 真实设备联调限制和不能自动判断的场景有明确记录。

### REQ-10 平台任务与外部任务隔离

当设备端自行启动文件时，监控必须将设备实际打印与 Farm 平台任务分开表达，不能仅凭打印机绑定关系更新平台任务。

验收标准：

- `READY` 等待启动任务只有在设备当前文件名与任务文件名明确匹配时才能进入 `PRINTING`。
- 设备文件名缺失或与平台任务不一致时，不得更新平台任务状态和进度。
- 外部任务仍按设备真实状态、文件名、进度和温度进行实时监控，并写入可区分来源的状态历史。
- 实时消息与历史接口返回 `FARM`、`EXTERNAL`、`UNKNOWN` 或 `NONE` 任务来源，以及关联的平台任务 ID 和判定原因。
- 前端列表和设备详情明确展示外部任务；外部任务结束后，原 `READY` 任务仍可继续由平台启动。
- 后端只在来源或文件发生变化时记录外部任务业务日志，避免轮询日志刷屏。

### REQ-11 持久化设备执行会话与 RRF 自然完成

RRF Standalone 在打印结束回到 `idle` 后可能清空进度、剩余时间和文件位置，系统必须根据已经确认的执行过程判断终态，而不能只依赖结束时的单帧数据。

验收标准：

- 平台任务只有在设备确认进入 `processing/paused` 且文件匹配后才建立 FARM 执行会话；仅上传的 `READY` 任务不得建立活动会话。
- 执行会话持久化打印机、平台任务、来源、文件、最大进度、设备 uptime 和最近状态，服务重启后仍可继续收尾。
- FARM 会话连续两次由执行态返回 `idle`，且无取消、中止、故障、重启或文件冲突证据时，任务自动完成。
- 任务终态、打印机解绑和执行会话关闭在同一事务中提交；失败时不得留下部分完成状态。
- 外部打印使用独立执行会话，结束时只关闭外部会话，不得完成或修改等待中的平台任务。
- 空闲状态下残留的 `lastFileName` 不得创建执行会话或认领平台任务。
