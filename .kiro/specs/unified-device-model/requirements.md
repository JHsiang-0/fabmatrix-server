# 统一设备模型完整落地与上报需求

状态：实施及分阶段验收进行中；创建日期：2026-11-02。本文是跨仓库需求基线，实际完成状态和证据以 [任务清单](tasks.md) 为准。

## 背景与目标

Server 已支持 Klipper/Moonraker 和 RRF，内部有部分 `PrinterObservation`；Cloud 当前使用 V1 和可选的受限 V2 快照，手机可以展示其中部分状态。当前 V2 不等于完整统一设备模型。完整领域设计及固件映射位于同级 `fabmatrix-cloud/docs/data-model/`，但其中 MySQL Server、接口状态和阶段日期等内容可能已过期，需要先与代码核对。

本任务先完成统一模型及其在现场、云端和手机上的必要存储、查询与兼容基础，再接入完整模型上报。保留原有现场手动打印、安全确认、权限和断网运行能力。设备不存在或固件不支持的数据应明确表示未知或不可用，不能伪造数值，也不能因追求“完整”而上传原始固件对象。

## 范围与验收需求

### R1 统一领域契约和所有权

1. 冻结本次交付的完整设备只读模型，至少覆盖来源实例、设备资产与稳定身份、归属与绑定、描述与能力、状态观测、实际执行及其与现场任务的关系、事件、告警和必要的遥测历史；给出字段、单位、数据质量、时间、可空性、上限、权限和所有权。
2. 明确任务、文件和用户由现场或 Cloud 哪一方管理；云端仅接收经授权的必要摘要，不把现场数字用户 ID 当成云身份，不复制整库。
3. 将产品版本、设备模型版本、上报协议版本和 HTTP API 版本分开管理；已部署的受限 V2 保持兼容，新协议版本号与协商机制须在设计冻结时确定。
4. 命令、远程控制、视频和文件传输作为独立领域边界；本轮不下发设备物理动作，但模型须保留其必要关联与权限边界。

### R2 设备身份与来源

1. Server 为数据库来源和现有/新增设备建立持久稳定标识；重启、升级和恢复后的身份规则明确，不能由 IP、名称或 MAC 单独推断身份。
2. Cloud 保留已存在的公开设备 ID；迁移和回填需可重入、可审计，不能因本地数字 ID 复用、网关重绑或克隆数据库而误合并设备。
3. 设备跨网关/来源转移必须有明确、受授权的归属确认与旧来源隔离规则；身份不确定时拒绝自动合并。

### R3 固件能力和统一采集

1. 为 Klipper/Moonraker 和 RRF 分别实现能力发现、设备描述和统一观测；工具、加热器、风扇、轴及传感器按证据建立关联，支持多工具及共享通道。
2. 对状态、温度、目标、功率、运动、任务进度、层数、耗材、运行时间和估算等已定义字段逐项标注来源和质量；支持、未知、未配置和固件不可获取明确区分。
3. 真实 0、未知、非法和不适用必须分开；单位、采样时间和有效期准确，RRF 多请求与 Klipper 更新间的数据一致性有明确规则。
4. 覆盖空闲、打印、暂停、过渡、故障、离线、模拟、设备重启和外部打印；不能将命令已接收等同设备动作已完成。

### R4 执行、事件、告警和历史

1. 建立稳定执行标识，复用并扩展当前 `farm_printer_execution`，保留与本地任务、外部打印及历史记录的关系；不能将未知结果当作完成。
2. 定义设备事件的稳定标识、去重、顺序和有界持久队列，断网重连不静默丢失已承诺的事件；状态最新值可按明确规则合并。
3. 建立必要的告警实例及确认记录、遥测采样/查询及有界保留策略，明确关闭或不支持时的行为；不要求建设自动派单或云端控制。
4. 当前观测与历史值分离，离线、超时、监控关闭、权限变化时不得把历史值呈现为实时值。

### R5 Server 持久化与本地兼容

1. 基于当前 SQLite 和 `LocalSchemaMigration` 设计可重复升级；全新库与旧库均验证，保留现有设备、用户、文件、任务和执行关系。
2. 最新模型具备持久化与版本策略，缓存不是唯一事实来源；写入、重启恢复、资源上限和事务边界明确。
3. 原有 LAN API、桌面客户端、WebSocket、设备监控、锁和任务安全流程保持兼容；云连接失败不影响现场业务。

### R6 完整模型上报与 Cloud 入站

1. 完整模型必须在 R1–R5 的契约、采集、持久化和 Cloud 消费基础通过验收后启用上报；原 V1/受限 V2 继续可用并可回退。
2. 完整库存、设备描述、观测、执行和事件分别具备边界、版本、大小限制、重试和提交确认；大库存分片未完整提交时不能隐藏设备。
3. 校验 MQTT 身份、组织/农场归属、绑定版本、启动代次、消息顺序、幂等和旧数据；重复、乱序、缺片、网络故障与重启不能造成数据错归属或静默丢失。
4. 传输只允许明确白名单，禁止原始凭据、API Key、私有地址、未授权文件路径或原始固件响应进入 Cloud、日志和客户端；具体文件/任务摘要须先确定授权。

### R7 Cloud 查询和手机体验

1. Cloud 按服务端身份和农场权限提供设备列表、完整详情及执行、事件、告警、历史的有界查询；跨组织/农场访问不得泄露存在性。
2. 旧列表和受限单设备状态接口继续支持旧客户端；完整详情不得把当前受限投影误称完整 canonical 对象。
3. 手机按能力展示完整设备详情及当前/历史状态，处理加载、空值、离线、过期、刷新失败、账号切换、权限撤销、小屏和大字；不直接访问固件或 MQTT。
4. 设备不存在、被完整库存移除、网关离线和观测过期应有不同且准确的显示语义。

### R8 测试、迁移与验收

1. 使用 Klipper、RRF 合成和脱敏 fixture 验证模型、转换和失败边界；涵盖多通道、真实零值、未知、状态转换和设备重启。
2. 隔离环境验证 SQLite 旧库升级/新库、Cloud MySQL/Flyway 升级、新旧协议及旧 App、权限隔离、重复/乱序/分片/重连及回滚；不使用真实打印机执行自动控制。
3. 分别记录一台真实 Klipper 与一台真实 RRF 的只读现场验收、安装版上报及手机端验收；未实际验证的状态不得标记完成。
4. 升级前核实数据与服务目标，给出备份、恢复、兼容与回退步骤；真实库变更和设备物理动作另按实际范围授权。

## 完成定义

任务全部完成并附带测试、数据库迁移、兼容性、安装版及手机验收证据；完整模型上报处于显式可观测、可关闭状态，不能把阶段性子集通过或模拟数据通过等同全部完成。
